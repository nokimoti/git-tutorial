しくみ A1

全体像 — Gitの中はオブジェクトと参照だけ

このステップのゴール

  • Git の内部構造をひとことで説明できるようになる
  • これから学ぶ「4種類のオブジェクト」と「参照」の言葉に慣れる

このトラックは何?

入門ステップでは git add や git commit などの「使い方」を学びました。 ここからは 「Git はその裏で何をしているのか」 という内部の仕組みを覗いていきます。 入門ステップを終えていなくても読めますが、コミット・ブランチ・HEAD の感覚があったほうが入りやすいです。

仕組みを知ると、「なぜブランチは一瞬で作れるのか」「なぜ Git は速いのか」 といった疑問が一気に氷解します。実際の操作にも自信が持てるようになります。
このトラックは専門用語が多めです。本文中の [このような囲み] はすべて用語集へのリンクです。意味がわからなくなったら、いつでもクリックして詳しい説明を見てください。

結論を先に言うと

Git の内部は驚くほどシンプルで、登場人物はたった2種類しかいません。

  1. オブジェクト — データ本体 (ファイルの中身、フォルダ構造、コミットなど)。ハッシュ で識別される
  2. 参照 (ref) — オブジェクトを指す目印 (実態は 1行だけのテキストファイル)
「ハッシュ」とは: 内容から計算される 40 文字の英数字。同じ内容なら必ず同じハッシュになる、いわば「データの指紋」です。詳しくは ハッシュ ページで。

4種類のオブジェクト

オブジェクトはさらに4種類に分かれます。これがすべての土台です。

種類役割このトラックで詳しく
blobファイルの中身そのものA2
treeフォルダ構造 (ファイル名 + blob)A3
commitスナップショット + 親コミット + 作者情報A4
tag (注釈付き)コミットへの注釈付きの目印—

参照 (ref) とは何か

ブランチ・HEAD・タグ (軽量タグ) はすべて、その実体は 「コミットの ハッシュ が1行だけ書かれたテキストファイル」 にすぎません。 これが Git の動作が軽い理由のひとつです。詳しくは A5 で見ます。

「ref (レフ)」は reference の略で、「指している先」 という意味。「あのコミットを指しているメモ」と思えばOK。

全体像

あなたのコミット履歴を裏側から見ると…

[HEAD] ──→ [ブランチ main] ──→ [commit] ──→ [tree] ──→ [blob]
                                    │           │         (ファイル内容)
                                    │           └→ [blob]
                                    │           └→ [tree (サブフォルダ)]
                                    │
                                    └→ [parent commit] ──→ [tree] ──→ [blob] …

矢印はすべて 「ハッシュで参照する」 という関係です。リポジトリの中はこのグラフが連なっただけ。

なぜこの仕組みが優秀?

  • 同じ内容は1つしか保存されない — 同じ blob は重複しない (容量節約)
  • ブランチが軽い — ファイル1つ作るだけ ([A5](05-refs.html))
  • 改ざんに強い — ハッシュチェーンで変更検出
  • 分散管理ができる — リポジトリ全体が自己完結
